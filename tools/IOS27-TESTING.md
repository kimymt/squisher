# iOS 27実機検証

対象ブランチ: codex/ios27-compatibility。HEIC入力検査を追加した開発版の比較試験。

## 起動

Macで `npm run dev -- --host 0.0.0.0` を実行し、表示されるNetwork URLの末尾に `/tools/ios27.html` を付ける。同じLANのiPhone Safariから開く。自己署名の開発用HTTPSなのでSafariで証明書確認が必要になる場合がある。開けない場合は表示されたエラーを確認する。
このページとTSはtools配下にあり、通常のVite本番buildには含まれない。既存Service Workerのキャッシュにも入れない。

## 最初に実施する試験

1. 自分で撮影した通常のHEIC写真1枚を使用する。まず12MPで行い、最初から48MPバッチにしない。
2. 入力経路を「写真ライブラリ」にし、機種・iOSビルドを記入して写真を選択する。
3. 標準/JPEGのまま「現行の検査・圧縮」「createImageBitmap」「画像要素」を順番に押す。各処理終了を待って次へ進む。
4. 生成画像の向き・色を確認する。生成成功後の共有ボタンは、必要に応じて保存を試す。共有APIの成功と、写真アプリへの実保存を区別する。
5. 同じ写真をFilesに用意し、入力経路をFilesへ変更して再度選び、同じ3試験を実施する。Filesへ書き出した時点で変換されていないか、入力形式の記録を確認する。
6. 「検証記録を保存」でJSONを保存し、このタスクに添付する。写真本体の添付は不要。目視での向き・色・写真保存の結果も知らせる。

記録はページのメモリ内だけで保持され、再読み込みで消える。ファイル名、画像本体、EXIFは記録しない。機種・OSの自由入力欄には個人情報を入力しない。
タイムアウトやタブ再読み込みが起きた場合は、その時点の結果を保存し、再読み込みしてから再試験する。OS内部のデコードを中断できる保証はない。

## 結果の読み方

- input.signatureがJPEGなら、入力時点でJPEGが渡っている。HEICという名前/MIMEだけで判断しない。
- HEIC-familyはftypの識別結果であり、ファイル全体の健全性や安全な寸法検査を保証しない。
- 最新mainはHEICヘッダーを未対応として拒否する。currentだけ失敗して直接試験が成功する場合は、デコード前検査にも対応が必要。
- bitmap失敗・element成功なら画像要素による代替経路の候補になる。
- 両方失敗する場合、外部コーデックなしで処理できるとは判断しない。
- 直接試験はデコード後に寸法上限を確認する比較用ツールであり、製品の入力検査を代替しない。

## HEIC入力検査追加後の再検証

ページを再読み込みし、前回と同じFilesのHEICを選択する。機種・OSビルドを記入し、まず標準/JPEGで「現行の検査・圧縮」を実行する。成功した場合は高品質・強力圧縮とWebPも試し、向き・色・保存結果を確認してJSONを保存する。失敗時もJSONを保存する。

今回追加した検査はhvc1と1階層grid、8〜10bit HEVCに限定する。主画像ID、関連付け、SPS寸法、グリッド寸法とタイルの一致、回転、データ範囲を確認し、既存の画素数・辺長制限を維持する。メタデータは1MiB、項目数は512まで。複数extent、画像シーケンス、iden/iovl等の派生項目、clap等の未対応プロパティは拒否する。ネイティブデコーダーの完全なビットストリーム検査を代替するものではない。

原本解析に基づき、主画像ではないtmapを限定対応した。参照先は主画像とhvc1/gridの補助画像の2つに限定し、回転後寸法・縦横比・補助画像の上限を照合する。tmapのパラメータは4KiB以下、uri型はhiddenのローカルメタデータのみ許可する。tmapが主画像の場合や入れ子のtmapは拒否する。原本での入力検査は4284×5712として成功した。ネイティブ処理の成立は実機再検証で判断する。画像要素へのfallbackは追加していない。

テスト用sample.heicは既存e2e/fixtures/sample.jpgをmacOS sipsで変換したもの。ユーザー提供写真はリポジトリに含めない。

## WebP選択肢制御の実装

1×1 CanvasのtoBlobで実際のWebP生成可否を1回確認し、結果を全行で共有する。未判定または非対応ならWebPボタンを無効化。JPEG入力はそのままJPEG圧縮を継続する。PNGの既定WebPが使えない場合は案内して停止し、透明部分が保持されないことを示したうえでユーザーがJPEGを明示選択できる。自動JPEG変換はしない。実画像の出力MIME一致検査も維持する。

生成可否チェックは2秒で終了し、失敗時は非対応として扱う（再読み込みで再判定）。UA判定・追加依存は使わず、既存の画像処理キュー内で実施。3品質・直列処理・入力上限は維持。

検証: 単体144件、E2E19件、本番ビルド成功。WebP要求がPNGを返す環境を模擬し、ボタン無効化、PNGの自動JPEG変換防止、明示選択後のJPEG成功を確認。ネイティブCanvasのない単体テスト環境ではgetContext未実装の出力あり。操作の検証はChromium E2Eで実施。

次の実機確認は /tools/ios27.html ではなく本体 / を再読み込みして行う。JPEG/HEICを選択してWebP無効化とJPEG保存を確認し、PNGは案内からJPEGへ切り替えた場合のみ圧縮されることを確認する。目視・保存と既存OS/48MP/ホーム画面版の確認は引き続き残る。

## 追加の自動検証と残る実機手順

追加E2E 2件成功。WebP非対応とHEICデコード失敗を模擬したPNG/HEIC/JPEG混在で、JPEGの完了、PNGの明示JPEG切り替え、保存対象件数の増加、最大同時デコード数1を確認。HEICデコードは意図的に失敗させたため、実機での混在成功を証明しない。

合成8064×6048 JPEG（48,771,072画素）をChromiumで処理。標準出力2560×1921を観測。厳密な短辺1920のテストは失敗し、長辺2560以下・縦横比からの短辺誤差1px以内という検証に修正して成功。写真画質、iOSメモリ挙動、48MP HEICの検証ではない。本番コードは変更していない。

実機では本体を再読み込みし、以下を順に確認する。

1. JPEG・HEIC・PNGを同時に選択する。JPEG/HEICが完了し、PNGが案内で止まること。PNGのJPEGを押すと、その画像も完了し、成功分を保存できること。
2. 48MP写真があれば1枚だけ選ぶ。3品質で完了し、タブの再読み込み・操作停止・欠けが起きないこと。写真アプリの情報欄で元の寸法も記録する。持っていなければ未確認のまま残す。
3. ホーム画面に追加した本体で起動し、JPEG/HEICの圧縮・写真保存を行う。Safariタブでの成功と別に記録する。
4. 既存iOSの端末が使える場合のみ、JPEG/PNGと対応範囲内のHEICで圧縮・保存を確認する。機種・OSバージョンとビルドを記録する。端末がなければ未確認として残し、UA模擬で代替しない。
